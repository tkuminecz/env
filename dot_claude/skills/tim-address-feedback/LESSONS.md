# Lessons — address-feedback

Read fully before Stage 1. Cap: 15 entries — adding #16 means pruning the weakest.
Each entry: the trap, then the check that avoids it. Curated by /tim-skill-gardener; don't
edit ad hoc mid-run (propose a lesson candidate in the run note instead).

1. Questions inside a feedback message get silently dropped — Tim has had to re-ask his own
   questions ("you never explained this", "what about this question?"). Enumerate every ask
   and close each one explicitly.
2. When Tim pushes back on a design point twice, switch to his direction — re-defending the
   same design in new words reads as not listening (column-overload debates took three
   rounds each).
3. Reported-done isn't done: replies, commits, and pushes have been claimed without landing
   ("I didn't see anything committed or pushed or any replies to Ian"). Verify each action's
   artifact before reporting it.
4. PR review replies have mechanics: identify the review's actual author and whether it's a
   code review or top-level comment before replying; use in_reply_to via REST, prefix as
   agent-on-behalf-of, include the fix's short commit ID, link the reply.
